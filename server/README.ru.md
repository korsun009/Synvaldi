# Сервер Synvaldi

ASP.NET Core 10 хранит аккаунты, устройства, логические профили, версии и бинарные файлы в PostgreSQL 17. Регистрация создаёт отдельный аккаунт Synvaldi. Для работы двух клиентов укажи на обоих один HTTPS-адрес и войди под одним логином.

## Запуск на Linux

В каталоге `server` положи пароль PostgreSQL **за пределами репозитория** и запусти отдельный проект Compose. Команды рассчитаны на оболочку Linux. Файл внутри закрытого каталога должен читаться системным пользователем контейнера API.

```sh
install -d -m 0700 "$HOME/.config/synvaldi"
secret="$HOME/.config/synvaldi/postgres-password"
if [ ! -e "$secret" ]; then
  (umask 077 && openssl rand -hex 32 > "$secret")
fi
chmod 0444 "$secret"
export SYNVALDI_DB_PASSWORD_PATH="$secret"
docker compose -p synvaldi up -d --build
curl -fsS http://127.0.0.1:8184/health
```

База доступна по внутренней сети Compose. API слушает loopback хоста на порту 8184. Пример для Caddy на этом же хосте, где DNS и TLS уже настроены для твоего домена:

```caddyfile
sync.example.org {
    reverse_proxy 127.0.0.1:8184 {
        flush_interval -1
    }
}
```

Для туннеля укажи backend `http://127.0.0.1:8184` на машине, где опубликован этот порт. URL в клиенте указывается до `/api/v1`. Не включай буферизацию событий SSE на прокси. Пароль базы при первом запуске задаёт роль PostgreSQL. Для смены этого пароля в существующем томе сначала измени пароль роли в БД, затем замени файл секрета и пересоздай API.

Для закрытого сервера после создания аккаунтов задай `SYNVALDI_REGISTRATION=false` и выполни `docker compose -p synvaldi up -d`. Для другого локального порта задай `SYNVALDI_PORT`. Процесс API также понимает `SYNVALDI_BLOB_QUOTA` в байтах. По умолчанию бинарное хранилище ограничено 2 ГиБ на аккаунт и 64 МиБ на один файл.

## Резервная копия и восстановление

Следующие команды выполняются в каталоге `server` с тем же `SYNVALDI_DB_PASSWORD_PATH`. Архив содержит профили, бинарные вложения и хеши паролей. Храни его с ограниченным доступом. Команда резервного копирования рассчитана на бинарное перенаправление Linux.

```sh
(umask 077 && docker compose -p synvaldi exec -T db pg_dump -U synvaldi -d synvaldi -Fc > synvaldi.dump)
docker compose -p synvaldi exec -T db pg_restore --list < synvaldi.dump
```

Для проверки создай **новую** БД под уникальным именем. Восстановление проходит одной транзакцией. При повторе проверки выбери свободное имя.

```sh
restore_db="synvaldi_check_$(date +%Y%m%d%H%M%S)"
docker compose -p synvaldi exec -T db createdb -U synvaldi "$restore_db"
docker compose -p synvaldi exec -T db pg_restore -U synvaldi \
  --single-transaction --exit-on-error --no-owner -d "$restore_db" < synvaldi.dump
docker compose -p synvaldi exec -T db psql -U synvaldi -d "$restore_db" \
  -c 'SELECT count(*) AS profiles, max(revision) AS last_revision FROM profile;'
```

Для проверки приложения подключи изолированный экземпляр API к восстановленной базе и проверь вход, профиль, старую версию и скачивание файла по его SHA-256. Секрет БД и настройки туннеля сохраняются отдельно от дампа. Полное восстановление сервиса требует также доступных Docker-образов или исходного кода соответствующей версии.

## Протокол

Все маршруты ниже имеют префикс `/api/v1`. В JSON используется camelCase. Токен передаётся через `Authorization: Bearer <token>`. Он хранится в БД только как SHA-256. Пароль хранится как PBKDF2-HMAC-SHA256 со случайной солью и 600 000 итераций. Токен устройства действует 180 дней. Повторный вход с тем же `deviceId` заменяет токен. Изменение пароля отзывает остальные сессии.

| Маршрут | Действие |
|---|---|
| POST /auth/register, /auth/login | `{username,password,deviceName,deviceId?}` → `{token,accountId,deviceId,username}`. Новый пароль от 8 до 1024 символов. |
| POST /auth/password, /auth/logout | Изменить пароль через `{currentPassword,newPassword}` или завершить текущую сессию. |
| GET /devices, PATCH/DELETE /devices/{id} | Список, имя через `{name}`, отзыв и сброс допуска. Unicode поддерживается. |
| PUT /devices/me/status | `{profileId,browserOnline,lastAppliedRevision}`. Сведения о применении сообщает клиент. |
| GET/POST /profiles, PATCH /profiles/{id} | Список, создать через `{name}`, переименовать. Повторное создание с тем же именем возвращает существующий профиль аккаунта. |
| POST /profiles/{id}/seed | Однократное заполнение непустым `{operationId,fields:{key:value}}` и допуск первого устройства. Создатель резервирует первоначальное заполнение до отзыва своего устройства. |
| GET /profiles/{id}/state | `{revision,fields:{key:{value,deleted,revision,guardRevision?}}}`. Сервер запоминает, какую ревизию запросившее устройство загрузило. |
| POST /profiles/{id}/admit | После успешного применения клиент подтверждает `{revision}`. Для нового устройства сервер проверяет факт запроса состояния и совпадение с текущей ревизией. При HTTP 409 повтори загрузку и применение. |
| POST /profiles/{id}/changes | `{operationId,offline,onlineLease?,changes:[{key,value,deleted,baseRevision,group?}]}` → `{revision,applied,conflicts}`. Для нового ключа базовая ревизия 0. |
| GET /profiles/{id}/history, /history/{revision} | Версии за скользящие 72 часа с устройством, временем, количеством изменённых ключей и первыми 20 именами. Из отдельной версии можно скачать весь снимок. |
| POST /profiles/{id}/rollback | `{operationId,revision}`. Восстановление создаёт новую ревизию. |
| GET/PUT /profiles/{id}/focus | Контекст окна, пространства и вкладки устройства. При чтении допустим `?deviceId={id}` другого устройства аккаунта. Ответ содержит время. |
| GET/POST /profiles/{id}/snapshots | Список ручных снимков или создать через `{name}`. Хранятся до удаления. |
| DELETE /profiles/{id}/snapshots/{snapshotId} | Удалить выбранный ручной снимок. |
| POST /profiles/{id}/snapshots/{snapshotId}/restore | Восстановить снимок через `{operationId}`. |
| GET/POST /profiles/{id}/trash | Список недавних удалений или переместить указанные поля в корзину через `{operationId,name,keys}`. ID записи равен ID операции. При удалении `workspace/{id}/exists` сервер включает остальные поля пространства и вкладок, у которых `workspaceId` указывает на него. |
| POST /profiles/{id}/trash/{itemId}/restore | `{operationId}`, доступно 30 суток. HTTP 409, если целевые поля уже изменились. |
| PUT/GET /blobs/{sha256} | Бинарное тело файла. SHA-256 проверяется на загрузке. Доступ ограничен аккаунтом. Файлы сохраняются независимо от удаления текущей ссылки, поэтому старые снимки и ручные копии сохраняют доступ к вложениям. |
| GET /events | SSE, `data: {"type":"online","onlineLease":"…"}` и `data: {"profileId":"…","revision":2}`. Начальная выдача включает все текущие ревизии аккаунта. |

Текущая запись и история фиксируются одной транзакцией под блокировкой строки профиля. Повтор той же операции от того же устройства возвращает исходный результат. При повторе ID с изменённым запросом сервер возвращает HTTP 409. Клиент сохраняет первоначальное тело до подтверждения, включая `onlineLease`. Порядок полей тела при повторной сериализации коллекций следует сохранять.

Клиент захватывает lease при создании изменения. Он действителен для текущего SSE-подключения и токена устройства. Новое подключение заменяет старый lease. При штатном разрыве сервер удаляет его, при потере процесса срок действия заканчивается за 35 секунд. С действующим lease для обычных полей побеждает последняя записанная транзакция. У операций без действующего lease и у отложенных изменений сервер сверяет базовую ревизию каждого поля. Группа изменений с одинаковым `group` применяется целиком либо отклоняется целиком. Удаление и откат ставят барьер: старая операция с более ранней базовой ревизией не запишется даже через действующий lease. При повторном подключении сначала загрузи облачный снимок и только затем отправь сохранённую очередь с её исходными базами.

PostgreSQL отправляет `NOTIFY` после фиксации. Каждый API-экземпляр слушает уведомления и оповещает подключённые устройства соответствующего аккаунта. Раз в 15 секунд поток повторно сверяется с БД, проверяет отзыв токена и обновляет lease. Клиент сам сообщает, что браузер применил ревизию. Сервер проверяет факт выдачи и подтверждения снимка, но не может самостоятельно наблюдать интерфейс Vivaldi.

История хранит старые значения затронутых полей. Начальная ревизия и каждая 128-я содержат полный снимок. Для просмотра сервер берёт ближайший более новый снимок или текущее состояние и отменяет изменения до выбранной версии. Это ограничивает реконструкцию 127 шагами. Срок хранения проверяется непосредственно при чтении. Фоновая очистка раз в 15 минут физически удаляет просроченную историю и корзину. Сохранённые пользователем полные снимки и квитанции обработки операций живут отдельно. После отзыва повторный вход устройства с прежним ID требует нового допуска, включая повтор уже обработанной операции.

## Проверка API

Для локальной разработки задай `SYNVALDI_DB` в формате строки Npgsql, при необходимости `SYNVALDI_DB_PASSWORD_FILE`, и выполни `dotnet run --project Synvaldi.Server.csproj`. Скрипт Python использует только стандартную библиотеку. Запускай его на одноразовой тестовой базе с включённой регистрацией: он создаёт собственные аккаунты, устройства и версии.

```sh
SYNVALDI_TEST_URL=http://127.0.0.1:8184 python3 tests/api.py
```

Для дополнительной проверки границы между контрольными снимками установи `SYNVALDI_TEST_CHECKPOINT=1`. Тест запишет 126 дополнительных транзакций и сверит выборочные версии до, на и после 128-й ревизии.
